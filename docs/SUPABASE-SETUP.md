# دليل إعداد Supabase لمنصة دورلي

> هذا الدليل مكتوب لصاحب المشروع. لا يحتاج خبرة برمجية عميقة — اتبع الخطوات بالترتيب.
> الوقت المتوقع للإعداد الأول: 20 إلى 30 دقيقة. كل ما تحتاجه: حساب على supabase.com، وصلاحية الدفع (push) إلى فرع `main` في مستودع GitHub.
>
> يطابق هذا الدليل **الإصدار v2** من المخطط (`supabase/migrations/20261017000000_init.sql`). القسم [8](#8-كيف-يعمل-النظام-من-الداخل-للمطورين) مرجع للمطورين، وبقية الأقسام لصاحب المشروع.

## ما الذي نبنيه؟

موقع دورلي موقع **ثابت** يُنشر على GitHub Pages — لا يوجد خادم خاص بنا. لذلك نستخدم **Supabase** ليقوم بدور الخادم:

| الخدمة | ما تقدّمه لدورلي |
|--------|------------------|
| **Postgres** (قاعدة بيانات) | الطلبات، العملاء، التجار، الموردون، المنتجات، المندوبون، وسجل أحداث كل طلب |
| **Auth** (تسجيل الدخول) | حسابات المديرين والمندوبين بالإيميل وكلمة السر |
| **Storage** (تخزين الملفات) | صور المنتجات (حاوية `product-images`) |
| **Realtime** | بث التغييرات على الطلبات وأحداثها للوحة التحكم لحظياً (مفعّل لجدولي `orders` و`order_events`) |

المتصفح يتصل بـ Supabase **مباشرة** بمفتاح عام اسمه `anon key`. الحماية كلها داخل قاعدة البيانات عبر سياسات **RLS** (Row Level Security) ومشغّلات حارسة مكتوبة في ملف واحد:

```
supabase/migrations/20261017000000_init.sql
```

هذا الملف هو "المخطط" الكامل: الجداول، الدوال، الصلاحيات، وحاوية الصور. ستنفّذه مرة واحدة في الخطوة 2.

### ماذا يحدث قبل الإعداد وبعده؟

| الحالة | الموقع العام | لوحة التحكم `/admin/` وبوابة المندوبين `/delegate/` |
|--------|--------------|------------------------------------------------------|
| **قبل الربط** (المفاتيح فارغة) | يعمل كما كان تماماً: نموذج الطلب يرسل إلى واتساب فقط، وزر التتبع يفتح واتساب | تعرض رسالة "قاعدة البيانات غير مهيأة بعد" مع خطوات الربط |
| **بعد الربط** | الطلب يُحفظ في القاعدة ويحصل الزبون على رقم تتبع `DW-2026-1001`، ويظل زر واتساب موجوداً | تعمل بالكامل |

هذه القاعدة مقصودة: لو تعطّلت Supabase لأي سبب، يبقى الموقع يعمل بواتساب.

## 1. إنشاء المشروع على supabase.com

1. افتح <https://supabase.com> وأنشئ حساباً (الأسهل: **Continue with GitHub** بنفس حساب المستودع).
2. اضغط **New project** واملأ:
   - **Name:** `dawerli`
   - **Database Password:** كلمة سر قوية. **احفظها في مكان آمن** — ستحتاجها لاحقاً (أداة CLI، النسخ الاحتياطي). لا علاقة لها بكلمة سر دخولك للوحة التحكم.
   - **Region:** `Central EU (Frankfurt)` — الأقرب لليبيا وأسرع استجابة.
   - **Plan:** Free (مجاني) يكفي للبداية. انظر [الترقية](#الترقية-إلى-الخطة-المدفوعة-pro--25-شهرياً) لاحقاً.
3. انتظر دقيقة أو دقيقتين حتى يصبح المشروع جاهزاً (الحالة الخضراء أعلى الصفحة).

> **ملاحظة:** الخطة المجانية تسمح بمشروعين نشطين فقط، وتوقف المشروع مؤقتاً بعد أسبوع بلا استخدام. التفاصيل في قسم [المشاكل](#المشروع-متوقف-paused-ولوحة-التحكم-تعرض-تعذر-الاتصال-بالخادم).

## 2. تنفيذ المخطط (migration)

عندك طريقتان. **الطريقة أ** أسهل ولا تحتاج تثبيت أي شيء.

### الطريقة أ — من لوحة Supabase (SQL Editor)

1. افتح ملف `supabase/migrations/20261017000000_init.sql` من المستودع (على GitHub اضغط **Raw** ثم انسخ كل المحتوى).
2. في لوحة Supabase: القائمة الجانبية → **SQL Editor** → **New query**.
3. الصق المحتوى كاملاً واضغط **Run** (أو `Ctrl+Enter`).
4. النتيجة المتوقعة: `Success. No rows returned`.
5. تأكد من **Table Editor**: ستجد الجداول `profiles`, `customers`, `merchants`, `suppliers`, `products`, `orders`, `order_events`. ومن **Storage**: حاوية `product-images`. ومن **Database → Replication** (أو **Realtime**): جدولا `orders` و`order_events` مضافان للبث.

> **نفّذ الملف مرة واحدة فقط.** تكراره يعطي خطأ `already exists` لأن الجداول صارت موجودة — وهذا طبيعي، لا تحذف شيئاً.

### الطريقة ب — من سطر الأوامر (Supabase CLI)

مناسبة للمطورين، وتحتاج Node.js على جهازك. أداة `supabase` مثبّتة كتبعية تطوير في المشروع فتعمل عبر `npx` بعد `npm install`، وملف `supabase/config.toml` موجود في المستودع (لا تحتاج `supabase init`):

```bash
npm install
npx supabase login                     # يفتح المتصفح لتسجيل الدخول
npx supabase link --project-ref XXXX   # XXXX = معرّف المشروع من رابط اللوحة: supabase.com/dashboard/project/XXXX
npx supabase db push                   # يطبّق ملفات supabase/migrations/ — سيطلب كلمة سر قاعدة البيانات
```

> اختر طريقة واحدة. إن نفّذت الملف يدوياً (أ) فلا تنفّذ `db push` بعدها على نفس المشروع.
> ملف `supabase/seed.sql` **لا** يُطبَّق بـ `db push` — هو للبيئة المحلية فقط.

## 3. إعدادات المصادقة (Auth)

في لوحة Supabase → **Authentication**:

### تأكيد الإيميل (اختياري — ننصح بتعطيله)

المسار: **Authentication → Sign In / Providers** (في اللوحات الأقدم: **Providers**) → **Email** → خيار **Confirm email**.

| الخيار | النتيجة |
|--------|---------|
| **معطّل** (موصى به) | المندوب يسجّل ويدخل فوراً. لا خطر: حسابه يبقى بدور "بانتظار الاعتماد" ولا يرى أي طلب حتى تعتمده الإدارة من `/admin/delegates/`. |
| **مفعّل** | المندوب يستلم رسالة تأكيد ولا يستطيع الدخول قبل الضغط على الرابط. **تنبيه:** خدمة الإيميل المدمجة في Supabase محدودة جداً (بضع رسائل في الساعة) ومخصصة للتجربة؛ للإنتاج تحتاج ضبط **SMTP** خاص من **Project Settings → Authentication → SMTP Settings**. |

### روابط الموقع

**Authentication → URL Configuration**:

- **Site URL:** `https://dawerli.org.ly`
- **Redirect URLs:** أضف `https://dawerli.org.ly/**` و (للتطوير) `http://localhost:4321/**`

هذه تُستخدم في روابط تأكيد الإيميل واستعادة كلمة السر إن فعّلتها.

### تأكد أن التسجيل مفتوح

**Authentication → Settings** (أو Sign In / Providers → General): خيار **Allow new users to sign up** يجب أن يبقى **مفعّلاً**، وإلا لن يستطيع المندوبون إنشاء حسابات من `/delegate/login/`. الحد الأدنى لكلمة السر 6 أحرف.

## 4. ربط الموقع بالمشروع: Project URL و anon key

### أين أجد القيمتين؟

لوحة Supabase → **Project Settings** (أيقونة الترس) → **API** (أو **API Keys**):

- **Project URL:** بالشكل `https://abcdefghijkl.supabase.co`
- **anon public key:** نص طويل يبدأ بـ `eyJ...` (في اللوحات الأحدث قد يُسمى **publishable key** ويبدأ بـ `sb_publishable_...` — كلاهما يعمل).

### هل نشر anon key آمن؟

**نعم.** هذا المفتاح مصمم ليُوضع في المتصفح، وهو يظهر في كود الموقع لأي زائر على كل حال. ما يحميك ليس سرّيته بل **سياسات RLS** داخل قاعدة البيانات: زائر الموقع (anon) لا يستطيع قراءة أي جدول مباشرة، فقط ينادي أربع دوال محددة (إنشاء طلب، الاستعلام عن حالة طلب برقمه، الرد على عرض السعر، وأرقام الصفحة الرئيسية).

### ⛔ المفتاح الذي لا يُنشر أبداً: `service_role`

في نفس الصفحة ستجد مفتاح **service_role** (أو **secret key**). هذا المفتاح **يتجاوز كل الحماية** — من يملكه يقرأ ويحذف كل البيانات. **لا تضعه أبداً** في أي ملف داخل المستودع، ولا في `supabase-config.js`، ولا في `.env.example`. إن تسرّب، أعد توليده فوراً من نفس الصفحة (**Reset**/**Rotate**).

وكذلك **كلمة سر قاعدة البيانات** من الخطوة 1: لا تُشارك ولا تُودع في المستودع.

### أين أضع القيمتين؟

الموقع يُبنى على GitHub Pages ولا يمكن تمرير متغيرات بيئة إلى عملية البناء هناك (ملف `deploy.yml` لا يحتاج أي تعديل)، لذلك توضع القيمتان **مباشرة في ملف الإعداد** `src/lib/supabase-config.js`. عدّل السطرين الأخيرين فقط:

```js
// قبل
export const SUPABASE_URL = (ENV_URL && String(ENV_URL).trim()) || '';
export const SUPABASE_ANON_KEY = (ENV_KEY && String(ENV_KEY).trim()) || '';

// بعد — ضع قيمك بين علامتي الاقتباس
export const SUPABASE_URL = (ENV_URL && String(ENV_URL).trim()) || 'https://abcdefghijkl.supabase.co';
export const SUPABASE_ANON_KEY = (ENV_KEY && String(ENV_KEY).trim()) || 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9....';
```

الجزء `ENV_URL && ...` يبقى كما هو: هو الذي يسمح للمطوّر محلياً باستخدام ملف `.env` بقيم مختلفة (انظر [التطوير المحلي](#9-التطوير-المحلي-للمطورين)) دون أن يلمس هذا الملف.

> **ملاحظة للمطورين:** بديل يُبقي الملف نظيفاً: ملف `.env.production` في جذر المشروع يحوي `PUBLIC_SUPABASE_URL=` و `PUBLIC_SUPABASE_ANON_KEY=`. هذا الملف غير مستثنى في `.gitignore` فيُودَع ويقرؤه Astro أثناء `npm run build`. أيّهما اخترت، لا تضع فيه إلا `anon key`.

## 5. النشر على الموقع الحي

1. اعتمد التغيير (commit) وادفعه (push) إلى فرع **`main`**. رسالة الاعتماد يجب **ألّا** تحتوي `[skip ci]` حتى يعمل النشر التلقائي:

   ```bash
   git add src/lib/supabase-config.js
   git commit -m "chore(supabase): ربط الموقع بمشروع Supabase"
   git push origin main
   ```

2. تابع **Actions** في صفحة المستودع على GitHub: عملية *Deploy Astro site to GitHub Pages* تستغرق 2 إلى 3 دقائق.
3. افتح <https://dawerli.org.ly/admin/login/>. إن ظهرت صفحة الدخول (وليس رسالة "غير مهيأة") فالربط نجح.

> إن بقيت رسالة "قاعدة البيانات غير مهيأة بعد": انظر [المشاكل](#لوحة-التحكم-تعرض-قاعدة-البيانات-غير-مهيأة-بعد-لم-يتم-الربط-بعد-رغم-وضع-المفاتيح).

## 6. أول حساب مدير

الحسابات الجديدة تُنشأ دائماً بدور **"بانتظار الاعتماد"** — حتى حسابك أنت. لذلك أول مدير يُرقّى يدوياً بالاستعلام المذكور أعلى ملف الـ migration:

1. افتح <https://dawerli.org.ly/delegate/login/> واختر تبويب **حساب مندوب جديد**. املأ الاسم، الهاتف، المدينة، الإيميل، وكلمة السر (6 أحرف على الأقل).
   - إن كان تأكيد الإيميل معطّلاً (الخطوة 3) تدخل فوراً وترى شاشة "حسابك بانتظار الاعتماد" — طبيعي، سنرقّيك الآن. إن كان مفعّلاً أكّده من الرسالة أولاً ثم سجّل دخولك.
2. في لوحة Supabase → **SQL Editor** → **New query**، الصق التالي بعد تغيير الإيميل إلى إيميلك (الإيميل يُنسخ تلقائياً من حساب الدخول إلى جدول `profiles`):

   ```sql
   update public.profiles set role = 'admin' where email = 'you@example.com';
   ```

   اضغط **Run**. النتيجة المتوقعة: `Success. 1 rows affected`. تأكد من **Table Editor → profiles** أن عمود `role` لحسابك صار `admin`.

   > لا تحتاج تعطيل أي مشغّل: SQL Editor يعمل بسياق موثوق تتجاوزه الحرّاس. من داخل الموقع، بالمقابل، لا يستطيع أحد ترقية نفسه.
3. افتح <https://dawerli.org.ly/admin/login/> وسجّل الدخول بنفس الإيميل وكلمة السر → تصل إلى **لوحة التحكم** `/admin/`.

> بعد ذلك لا تحتاج SQL Editor لاعتماد المندوبين أو ترقية مديرين آخرين — كل هذا من صفحة **المندوبون** `/admin/delegates/`. القاعدة تمنع إزالة أو إيقاف **آخر مدير نشط** (خطأ `last_admin`) حتى لا تُقفل اللوحة على نفسك.

## 7. تجربة كاملة: طلب → تتبع → مندوب

### أ) طلب من الموقع وتتبعه

1. افتح <https://dawerli.org.ly/request/> واملأ طلباً تجريبياً برقم هاتف ليبي صحيح (10 أرقام تبدأ بـ `09`؛ الأرقام العربية والمسافات و`+218` تُطبَّع تلقائياً).
2. بعد الإرسال يظهر **رقم التتبع** بالشكل `DW-2026-1001` (الأرقام تبدأ من 1001 وتزيد تلقائياً)، مع زر واتساب كالمعتاد.
3. افتح <https://dawerli.org.ly/track/> وأدخل الرقم: يظهر الخط الزمني بحالة **"استلمنا طلبك"**. صفحة التتبع تعرض الحالة والمدينة والفئة والكمية وملاحظات الفريق — **لا تعرض اسم الزبون ولا هاتفه** لأن الرقم قد يُشارك. عند حالة **عرض السعر** يظهر صندوق "حط رقمك اللي طلبت بيه باش تشوف السعر": بعد إدخال **هاتف الزبون المطابق** تظهر الأسعار (السعر المعروض، رسوم الخدمة، الإجمالي) مع زرّي **موافق** / **مش موافق** — القاعدة لا تُرجع الأسعار ولا تقبل الرد بدون الهاتف المطابق.
4. في لوحة التحكم → **الطلبات** `/admin/orders/`: الطلب موجود بكامل بياناته، والعميل أُنشئ تلقائياً في **العملاء** بهاتفه (الطلبات اللاحقة بنفس الهاتف تُربط بنفس العميل). إن كان الهاتف لتاجر مسجّل في **التجار** يُربط الطلب به تلقائياً أيضاً.

### ب) دورة حياة الطلب

| الحالة في القاعدة | ما يراه الزبون | المرحلة في الخط الزمني | من ينقل الطلب إليها |
|-------------------|----------------|------------------------|---------------------|
| `received` | استلمنا طلبك | 1 | تلقائياً عند الإرسال (أو الإدارة عند إلغاء تعيين مندوب) |
| `searching` | ندوّروا ونسعّروا | 2 | المندوب بالحجز، أو الإدارة بالإسناد |
| `quoted` | عرض السعر — بانتظار موافقتك | 3 | المندوب أو الإدارة من `searching` |
| `purchasing` | الشراء والتجهيز | 4 | من `searching` أو `quoted` |
| `shipping` | في الطريق ليك | 4 | من `purchasing` |
| `delivered` | تم التسليم | 5 | من `shipping` |
| `cancelled` | ملغي | — | **الإدارة فقط** (مع سبب الإلغاء) |

- كل تغيير حالة يُسجَّل تلقائياً في **سجل الأحداث** (`order_events`) ويظهر في صفحة التتبع. أحداث الإسناد/إلغاء الإسناد داخلية ولا تظهر للزبون.
- **الملاحظة** المرفقة مع تغيير الحالة تظهر للزبون في صفحة التتبع (مثلاً: "لقينا القطعة بسعر 420 د.ل + 30 رسوم خدمة، ننتظر موافقتك"). ملاحظة بلا تغيير حالة تُسجَّل كحدث ملاحظة.
- عند حالة **عرض السعر** يستطيع الزبون (برقم الطلب + هاتفه) قبول العرض أو رفضه؛ ردّه يُحفظ على الطلب ويظهر كملاحظة في السجل.
- **الإدارة** تستطيع كل شيء: أي انتقال (للأمام أو للخلف)، الإلغاء مع سبب، تعديل بيانات الزبون والملاحظات الداخلية وعمولة المندوب.
- **المندوب** يحرّك طلباته **للأمام فقط** وفق هذا المسار الصارم:
  `received → searching`، `searching → quoted` أو `purchasing`، `quoted → purchasing`، `purchasing → shipping`، `shipping → delivered`.
  لا يستطيع الإلغاء ولا الرجوع ولا تعديل بيانات الزبون، ولا يلمس طلباً **مسلَّماً** أو **ملغياً** (مجمّدان). يستطيع تعديل: الحالة، المورد، المنتج، السعر المعروض، رسوم الخدمة، والإجمالي — والقاعدة نفسها ترفض ما عدا ذلك حتى لو حاول من خارج الموقع.

### ج) اعتماد مندوب وعمله

1. المندوب يفتح <https://dawerli.org.ly/delegate/login/> → تبويب **حساب مندوب جديد**. بعد الدخول يرى رسالة **"حسابك بانتظار الاعتماد"** ولا شيء غيرها.
2. أنت من لوحة التحكم → **المندوبون** `/admin/delegates/` → تعتمد حسابه (الدور يصبح **مندوب** ويُسجَّل تاريخ الاعتماد تلقائياً). من نفس الصفحة يمكنك إيقاف حساب (`active = false`) أو ترقية مدير آخر. **لا يوجد حذف** للحسابات من اللوحة — الإيقاف بدل الحذف.
3. المندوب يحدّث الصفحة فتنفتح له بوابته:
   - **طلبات متاحة** `/delegate/` — كل الطلبات الجديدة (`received`) التي لم يحجزها أحد، مرتبة بالاستعجال (عاجل → متوسط → عادي) ثم بالأقدم، **بدون اسم الزبون أو هاتفه**. زر **حجز** يسند الطلب له وينقله إلى "ندوّروا ونسعّروا". لا يمكن لمندوبين حجز نفس الطلب — من يضغط أولاً يفوز والآخر يرى رسالة "سبقك مندوب آخر على هذا الطلب".
   - **حد الطلبات الجارية: 5.** المندوب الذي عنده 5 طلبات في الحالات `searching/quoted/purchasing/shipping` لا يستطيع حجز طلب جديد حتى يسلّم أحدها (رسالة "عندك 5 طلبات جارية").
   - **طلباتي** `/delegate/mine/` — طلباته المحجوزة بكامل بياناتها (الاسم والهاتف يظهران بعد الحجز فقط، بلا الملاحظات الداخلية للإدارة)، مع تحديث الحالة والسعر ورسوم الخدمة وإضافة ملاحظة للزبون.
4. الموردون والمنتجات النشطة تظهر للمندوب **للقراءة فقط** لتساعده في البحث والتسعير.
5. الإدارة تستطيع أيضاً إسناد طلب لمندوب معيّن (أو سحبه منه) من لوحة الطلبات بدل انتظار الحجز.

### مصفوفة الصلاحيات (كما تفرضها القاعدة)

| الدور | ما يستطيعه |
|-------|------------|
| **زائر** (anon) | إنشاء طلب · الاستعلام عن حالة طلب برقمه (والأسعار بهاتفه) · الرد على عرض السعر · أرقام الصفحة الرئيسية. **لا وصول مباشر لأي جدول.** حد مضاد للإغراق: 5 طلبات لكل هاتف و600 طلباً إجمالاً كل 10 دقائق. |
| **بانتظار الاعتماد** (pending) | لا شيء سوى رؤية وتعديل ملفه الشخصي (بلا دوره أو تفعيله). |
| **مندوب** (delegate) | رؤية الطلبات المتاحة (أعمدة محدودة) · حجز طلب (بحد 5 جارية) · رؤية وتحديث طلباته فقط للأمام · إضافة ملاحظات عليها · قراءة الموردين والمنتجات النشطة · إحصائياته الشخصية. |
| **مدير** (admin) | كل شيء، بما فيه اعتماد/إيقاف المندوبين، الإسناد، الإلغاء، وإدارة العملاء والتجار والموردين والمنتجات ورفع صور المنتجات. |

## 8. كيف يعمل النظام من الداخل (للمطورين)

مرجع مختصر لما يفرضه المخطط v2. الكود في المتصفح يستخدم `src/lib/db.js` (الذي يلفّ هذه الدوال) ولا يعدّل الجداول مباشرة إلا من لوحة الإدارة.

### الأدوار والسياق الموثوق

- `profiles.role` ∈ `pending | delegate | admin`، مع `active` و`approved_at` و`email` (يُنسخ من `auth.users` عند التسجيل وعند تغيير الإيميل).
- `is_admin()` / `is_delegate()` تشترطان `active = true`.
- **السياق الموثوق** (`is_trusted_context()`): كل ما ليس `anon`/`authenticated` — المالك، `service_role`، SQL Editor، والـ seed. الحرّاس لا يعترضونه؛ لذلك ترقية أول مدير وحذف بيانات عميل تتمّان من SQL Editor بلا تعطيل مشغّلات.
- حارس `profiles`: غير المدير لا يغيّر `role/active/email/approved_at`؛ المدير لا يستطيع إزالة آخر مدير نشط (`last_admin`). الانتقال `pending → delegate` يملأ `approved_at` تلقائياً. لا سياسة DELETE على `profiles` — التعطيل بدل الحذف (الحذف الفعلي عبر `auth.users` من لوحة Supabase، ويتسلسل إلى الملف).

### تغيير الحالة والإسناد (استخدم الدوال، لا `update` مباشر)

**`set_order_status(p_order_id, p_status, p_note, p_quoted_price, p_service_fee, p_total, p_cancel_reason)`** هي الطريقة الوحيدة المعتمدة لتغيير حالة طلب — للمدير والمندوب معاً. تعمل بصلاحيات المستدعي (SECURITY INVOKER) فتبقى RLS والحارس ساريين: المندوب يُرفض عند أي انتقال خارج المسار أو على طلب ليس له. تحدّث الحالة والأسعار في عملية واحدة (إن مُرّر سعر أو رسوم بلا إجمالي يُحسب `total = quoted_price + service_fee`)، وتسجّل **حدثاً واحداً فقط** يحمل الملاحظة (لا تكرار)؛ وإن كانت الحالة نفسها مع ملاحظة، يُسجَّل حدث من نوع `note`. المشغّلات تختم الطوابع تلقائياً: `status_changed_at` دائماً، `quoted_at` عند `quoted`، `delivered_at/delivered_by` عند `delivered`، `cancelled_at/cancelled_by` عند `cancelled`. **`assign_order(p_order_id, p_delegate_id | null, p_note)`** للإدارة فقط: تعيين مندوب (نشط بدور delegate أو admin) ينقل `received → searching`، وإلغاء التعيين (`null`) يعيد `searching → received` فيرجع الطلب لقائمة المتاحة؛ تسجّل حدث `assign`/`unassign` غير ظاهر للزبون، وترفض الطلبات المسلّمة/الملغاة. **`claim_order(p_order_id)`** للمندوب: يحجز طلباً `received` بلا مندوب (من يسبق يفوز، `false` إن سُبق)، ويرفع `too_many_active` عند 5 طلبات جارية.

### القراءة: الـ views

| الـ view | من يقرؤه | المحتوى |
|----------|----------|---------|
| `delegate_open_orders` | المندوب والمدير | الطلبات `received` بلا مندوب، أعمدة محدودة (بلا اسم/هاتف)، مع `urgency_rank` (0 عاجل، 1 متوسط، 2 عادي). استعلام الصفحة: `.order('urgency_rank').order('created_at')`. |
| `delegate_my_orders` | المندوب (security_invoker — RLS على `orders` يبقى سارياً) | طلباته هو، بكامل بيانات الزبون وبلا `internal_notes` أو `delegate_commission` أو `cancel_reason`. التحديث يبقى عبر `set_order_status`. |

الإدارة تقرأ `orders` مباشرة. ملاحظة PostgREST: لجدول `orders` ثلاثة مفاتيح أجنبية إلى `profiles` (`delegate_id`, `delivered_by`, `cancelled_by`) فالتضمين يجب تمييزه: `delegate:profiles!orders_delegate_id_fkey(full_name,phone,email)`.

### سجل الأحداث `order_events`

- `kind` ∈ `status | note | assign | unassign`، و`visible_to_customer` (افتراضياً true؛ أحداث الإسناد false).
- حارس قبل الإدراج: إدراج المندوب يُجبر على `kind = 'note'` بحالة الطلب الحالية، `actor_id = auth.uid()`، `created_at = now()`، ويُرفض بلا نص أو على طلب ليس له. المدير يدرج بحرية.
- `get_order_status` يُرجع للزبون فقط الأحداث الظاهرة من النوعين `status` و`note`.

### الدوال العامة (anon)

| الدالة | تُرجع |
|--------|-------|
| `submit_order(p jsonb)` | `{ id, code }`. تتحقق من الهاتف الليبي، الاسم، المدينة، الفئة؛ `urgency` ∈ عادي/متوسط/عاجل؛ `source = 'web'`؛ حد الإغراق 5/هاتف و600/إجمالي كل 10 دقائق. |
| `get_order_status(p_code, p_phone?)` | `code, status, stage_idx (−1 للملغي), status_label, city, category, quantity, created_at, updated_at, status_changed_at, delivered_at, cancelled_at, cancel_reason (للملغي فقط), verified, events[]` — و`quoted_price/service_fee/total/quote_response` **فقط** عند `verified` (الهاتف مطابق). يقبل الرقم بلا بادئة `DW-` وبأرقام عربية. |
| `respond_to_quote(p_code, p_phone, p_accept)` | `true/false`. يعمل فقط على طلب بحالة `quoted` بهاتف مطابق؛ يحفظ `quote_response` ويسجّل ملاحظة ظاهرة للزبون. |
| `public_stats()` | `{ delivered_orders, customers, cities, avg_delivery_hours }`. |

### إحصائيات اللوحات

- `admin_stats()` — للمدير فقط (تُرجع `null` لغيره): `today, open, unassigned, delivered_month, fees_month, cancelled_month, avg_delivery_hours, customers, merchants, suppliers, products, pending_delegates, by_status`. الشهر/اليوم بتوقيت `Africa/Tripoli`.
- `delegate_stats()` — للمندوب: `{ open_pool, active, delivered_month, delivered_total, commission_month }` (العمولة من عمود `delegate_commission` الذي تحدده الإدارة).

### Realtime والتخزين

- جدولا `orders` و`order_events` مضافان إلى `supabase_realtime`؛ الاشتراكات تخضع لـ RLS نفسها (المندوب لا يستقبل إلا طلباته).
- حاوية **`product-images`** عامة القراءة: الحد **5MB** للملف، الأنواع **`image/jpeg`, `image/png`, `image/webp`** فقط، والرفع/التعديل/الحذف للمدير فقط وتحت المسار **`products/`** (مثل `products/<uuid>.webp`).

### إضافة تغيير على المخطط لاحقاً

لا تعدّل `20261017000000_init.sql` بعد تطبيقه على الإنتاج. أنشئ ملف migration جديداً:

```bash
npx supabase migration new add_something   # يُنشئ supabase/migrations/<timestamp>_add_something.sql
npx supabase db reset                      # جرّبه محلياً (migrations + seed)
npx supabase db push                       # ثم طبّقه على الإنتاج (بعد link)
```

## 9. التطوير المحلي (للمطورين)

لتجربة الموقع ولوحة التحكم على جهازك بقاعدة بيانات محلية منفصلة عن الإنتاج، بحسابات وبيانات جاهزة.

### المتطلبات

- **Node.js** 20+
- **Docker Desktop** (على Windows يحتاج WSL2) — شغّله قبل الخطوة التالية.

### التشغيل

```bash
npm install
npx supabase start         # أول مرة ينزّل صور Docker (قد يستغرق دقائق) — يقرأ supabase/config.toml الموجود في المستودع
npx supabase status        # يطبع العناوين والمفاتيح المحلية
```

خرج `status` يشبه:

```
         API URL: http://127.0.0.1:54321
          DB URL: postgresql://postgres:postgres@127.0.0.1:54322/postgres
      Studio URL: http://127.0.0.1:54323
     Mailpit URL: http://127.0.0.1:54324
        anon key: eyJhbGciOi...        ← (في إصدارات CLI الأحدث: Publishable key: sb_publishable_...)
service_role key: eyJhbGciOi...        ← لا تستخدمه في الموقع حتى محلياً
```

أنشئ ملف `.env` في جذر المشروع (انسخه من `.env.example`) وضع فيه القيمتين المحليتين:

```env
PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
PUBLIC_SUPABASE_ANON_KEY=<anon key من خرج status>
```

ثم:

```bash
npm run dev                # http://localhost:4321
```

`.env` مستثنى في `.gitignore` فلن يصل للمستودع، وقيمه تتقدّم على القيم المكتوبة في `supabase-config.js` — فالمطوّر يعمل على القاعدة المحلية دون أن يلمس ملف الإنتاج.

### الحسابات والبيانات الجاهزة

عند أول `supabase start` (وعند كل `db reset`) تُطبَّق ملفات `supabase/migrations/` ثم `supabase/seed.sql`، فتجد:

| الحساب | كلمة السر | الدور |
|--------|-----------|-------|
| `admin@dawerli.local` | `admin12345` | مدير |
| `delegate@dawerli.local` | `delegate12345` | مندوب معتمد |
| `pending@dawerli.local` | `pending12345` | بانتظار الاعتماد |

بالإضافة إلى 3 موردين، 3 منتجات، تاجرين، و8 طلبات بحالات مختلفة (`DW-2026-1001` إلى `DW-2026-1008`؛ الطلبات الجديدة محلياً تبدأ من `DW-2026-1101`). تأكيد الإيميل معطّل محلياً (`enable_confirmations = false` في `config.toml`).

> `seed.sql` للبيئة المحلية **فقط**. لا تنفّذه على مشروع الإنتاج.

### أوامر مفيدة

```bash
npx supabase db reset      # يمسح القاعدة المحلية ويعيد تطبيق migrations + seed
npx supabase stop          # يوقف الحاويات (البيانات تبقى)
npx supabase stop --no-backup   # يوقفها ويمسح البيانات
```

- **Studio المحلي** <http://127.0.0.1:54323>: مثل لوحة Supabase لكن لقاعدتك المحلية (Table Editor, SQL Editor, Auth).
- **Mailpit** <http://127.0.0.1:54324>: يلتقط كل الإيميلات (تأكيد، استعادة كلمة سر) بدل إرسالها.

### اختبار الصلاحيات (RLS smoke test)

ملف `supabase/tests/rls_smoke.sql` يفحص على القاعدة المحلية كل قواعد القسم 8 (الزائر لا يقرأ الجداول، المندوب لا يرجع للخلف ولا يلغي ولا يعدّل بيانات الزبون، حد الـ 5 طلبات، `last_admin`، ختم الطوابع، حدث واحد لكل تغيير حالة…). شغّله بعد `db reset` — كل سطر نتيجة يبدأ بـ `OK` أو `FAIL`، ولا يُفترض ظهور `ERROR` خام:

```bash
npx supabase db reset
docker exec -i supabase_db_cloud-local-deployment-cc7fad psql -U postgres -d postgres -v ON_ERROR_STOP=0 < supabase/tests/rls_smoke.sql
```

(اسم الحاوية هو `supabase_db_` + قيمة `project_id` في `config.toml`.) الاختبار يعدّل بيانات القاعدة المحلية، فأعد `db reset` بعده إن أردت بيانات seed نظيفة. عند تعديل المخطط لاحقاً، أضف حالات الاختبار الجديدة هنا.

## 10. الأسئلة الشائعة والمشاكل

### المشروع متوقف (Paused) ولوحة التحكم تعرض "تعذّر الاتصال بالخادم"

الخطة المجانية **توقف المشروع مؤقتاً بعد أسبوع بلا أي طلبات**. عند التوقف: الموقع العام يستمر بواتساب، لكن حفظ الطلبات والتتبع ولوحة التحكم تتوقف.

- **الحل:** افتح لوحة Supabase → المشروع → زر **Restore project**. يعود خلال دقائق بكل بياناته.
- **لتجنّبه نهائياً:** [الترقية إلى Pro](#الترقية-إلى-الخطة-المدفوعة-pro--25-شهرياً). الزيارات المنتظمة للموقع تُبقيه نشطاً عادةً، لكن لا تعتمد على ذلك.

### لوحة التحكم تعرض "قاعدة البيانات غير مهيأة بعد" (لم يتم الربط بعد) رغم وضع المفاتيح

معنى الرسالة: الكود المنشور لا يحتوي رابط مشروع صالحاً يبدأ بـ `http(s)://` ومفتاحاً أطول من 20 حرفاً — أي أن الموقع يعمل في وضع "واتساب فقط" ولم يُربط بعد. الأسباب المعتادة:

- التغيير لم يصل فرع `main`، أو عملية **Actions** لم تكتمل (أو رسالة الاعتماد تحوي `[skip ci]`).
- الرابط لا يبدأ بـ `https://`، أو المفتاح نُسخ ناقصاً أو بمسافات.
- كاش المتصفح: حدّث الصفحة بقوة (`Ctrl+F5`).
- محلياً: ملف `.env` غير موجود أو القيم فارغة، أو لم تُعد تشغيل `npm run dev` بعد إنشائه.

### نسيت كلمة السر (مدير أو مندوب)

الموقع لا يحتوي حالياً صفحة "نسيت كلمة السر"، لذلك يغيّرها المدير من **SQL Editor** في لوحة Supabase:

```sql
update auth.users
   set encrypted_password = crypt('كلمة-السر-الجديدة', gen_salt('bf'))
 where email = 'user@example.com';
```

ثم أبلغ صاحب الحساب بكلمة السر الجديدة. (بديل من اللوحة: **Authentication → Users** → الحساب → **Send password recovery** — يحتاج صفحة استعادة في الموقع غير موجودة بعد، فاستخدم SQL.)

### المندوب يقول "ما عندكش صلاحية" أو "حسابك بانتظار الاعتماد"

- لم يُعتمد بعد: **لوحة التحكم → المندوبون** → اعتمده.
- حسابه موقوف (`active = false`): فعّله من نفس الصفحة ("حسابك موقوف").
- يحاول فتح `/admin/` وهو مندوب: صفحته هي `/delegate/`.
- يحاول نقل طلب للخلف أو إلغاءه أو تعديل بيانات الزبون: ممنوع على المندوب بالتصميم — تتولاه الإدارة.

### "عندك 5 طلبات جارية"

حد مقصود: المندوب لا يحجز طلباً جديداً وعنده 5 طلبات غير مسلّمة. الحل: يسلّم أحدها، أو تسحب الإدارة طلباً منه (إلغاء تعيين من لوحة الطلبات). لتغيير الرقم 5 يلزم migration جديد يعدّل `claim_order`.

### "ما ينفعش — هذا آخر مدير نشط"

القاعدة ترفض إزالة أو إيقاف آخر مدير نشط (`last_admin`). رقِّ مديراً آخر أولاً ثم غيّر الحساب الحالي.

### "أكّد إيميلك من الرسالة اللي وصلتك أولاً"

تأكيد الإيميل مفعّل والرسالة لم تصل (أو انتهى حد الإرسال المجاني). إما عطّل **Confirm email** (الخطوة 3)، أو أكّد الحساب يدوياً: **Authentication → Users** → الحساب → **Confirm email**.

### "وصلتنا طلبات كثيرة من رقمك في وقت قصير"

حماية مقصودة ضد الإغراق: 5 طلبات لكل رقم هاتف كل 10 دقائق، و600 طلب إجمالاً من الموقع كل 10 دقائق. انتظر قليلاً أو أرسل بواتساب.

### حذف بيانات عميل (طلب من الزبون)

في **SQL Editor** (سياق موثوق — لا حاجة لتعطيل أي مشغّل). الطلبات تبقى للإحصاء لكن بلا اسم أو هاتف حقيقي. استخدم الهاتف بالصيغة المطبّعة `09XXXXXXXX`:

```sql
-- 1) إخفاء هوية العميل في طلباته
update public.orders
   set customer_name = 'عميل محذوف',
       customer_phone = 'deleted-' || left(id::text, 8),
       customer_id = null
 where customer_phone = '0912345678';

-- 2) حذف سجل العميل
delete from public.customers where phone = '0912345678';
```

ملاحظات المندوبين في `order_events` لا تحوي بيانات شخصية عادةً، لكن راجعها من **الطلبات** إن كتب أحدهم اسم الزبون فيها. بعد الحذف لن يعمل التتبع بالهاتف ولا الرد على عرض السعر لتلك الطلبات (مقصود).

### حذف حساب مندوب نهائياً

لا يوجد حذف من اللوحة بالتصميم — **الأفضل إيقاف** الحساب من `/admin/delegates/`. إن أردت الحذف الفعلي: **Authentication → Users** → الحساب → **Delete user**. ملفه الشخصي يُحذف تلقائياً، وطلباته تبقى لكن بلا مندوب على حالتها الحالية (مثلاً `searching`) فلا تظهر في قائمة المتاحة. من لوحة **الطلبات** أسندها لمندوب آخر، أو ألغِ التعيين لتعود `received` وتظهر للمندوبين.

### النسخ الاحتياطي

- **الخطة المجانية لا تحتوي نسخاً احتياطياً تلقائياً.** المخطط نفسه محفوظ في المستودع (ملف migration)، لكن **البيانات** مسؤوليتك:
  - يدوياً: **Table Editor** → الجدول → **Export** → CSV، لكل جدول مهم (`orders`, `customers`, `order_events` على الأقل).
  - بأداة CLI (بعد `link`): `npx supabase db dump --linked --data-only -f backup-data.sql` — ينتج ملف SQL بكل البيانات. احفظه خارج المستودع (يحوي بيانات زبائن).
  - صور المنتجات في **Storage → product-images** تُنزَّل من اللوحة.
- **خطة Pro:** نسخ تلقائي يومي يُحفظ 7 أيام مع استعادة بضغطة من **Database → Backups**.

### الترقية إلى الخطة المدفوعة (Pro — 25$ شهرياً)

متى تحتاجها: عندما يصبح الموقع مصدر عمل يومي ولا تقبل توقّفه.

ما تحصل عليه مقابل 25$/شهر للمنظمة (راجع صفحة الأسعار للأرقام الحالية):
- **لا توقف تلقائياً** للمشروع.
- **نسخ احتياطي يومي** تلقائي.
- حدود أعلى بكثير: قاعدة بيانات 8GB، تخزين 100GB، 100 ألف مستخدم نشط شهرياً.
- دعم عبر الإيميل.

المسار: لوحة Supabase → **Organization settings → Billing → Upgrade**. لا يتغير شيء في كود الموقع.

### أريد البدء من الصفر على الإنتاج

الأسهل: احذف المشروع من **Project Settings → General → Delete project** وأنشئ مشروعاً جديداً (الخطوات 1 إلى 6). المفاتيح ستتغير فأعد الخطوة 4. **كل البيانات تُحذف** — خذ نسخة أولاً.

## 11. مرجع سريع

### الروابط

| الصفحة | الرابط |
|--------|--------|
| نموذج الطلب | `/request/` |
| تتبع طلب | `/track/` |
| دخول الإدارة | `/admin/login/` |
| لوحة التحكم | `/admin/` ثم `/admin/orders/` `/admin/customers/` `/admin/merchants/` `/admin/suppliers/` `/admin/products/` `/admin/delegates/` |
| دخول / تسجيل المندوبين | `/delegate/login/` |
| بوابة المندوبين | `/delegate/` (طلبات متاحة) · `/delegate/mine/` (طلباتي) |

صفحات `/admin/` و `/delegate/` مستثناة من محركات البحث (`noindex` + `robots.txt`).

### الجداول

| الجدول | المحتوى |
|--------|---------|
| `profiles` | المديرون والمندوبون (مرتبط بحسابات Auth؛ يُنشأ تلقائياً عند التسجيل بدور `pending`؛ يحوي `email`, `active`, `approved_at`) |
| `customers` | العملاء — فريدون بالهاتف، يُنشؤون تلقائياً من الطلبات |
| `merchants` | التجار (أصحاب المحلات الذين يطلبون بالجملة) — يُربط الطلب بهم تلقائياً بالهاتف |
| `suppliers` | الموردون الذين نشتري منهم (تصنيفات + تقييم) |
| `products` | منتجات/قطع معروفة بنطاق سعر وصورة ومورد |
| `orders` | الطلبات: بيانات الزبون، التفاصيل، الحالة، المندوب، الأسعار، عمولة المندوب، ردّ الزبون على العرض، سبب الإلغاء، والطوابع الزمنية لكل مرحلة |
| `order_events` | سجل أحداث كل طلب (`status/note/assign/unassign` + ملاحظة + ظهورها للزبون + من قام بها) |
